# 思维树提示 Skill

## 示例1：结构化决策问题

### 用户任务及输出格式

任务：为一个复杂产品方案选择最优路线。

输出格式：展示思维树过程表、最终选择和简短理由。

### 生成的思维树 Prompt

```
你是一名严谨的多路径决策助手。

请使用 Tree of Thoughts（思维树）方法处理任务。你的目标不是沿着单一路径直接回答，而是在有限分支和有限深度内探索多个候选思路，评价并剪枝，最后选择或综合最优路径给出答案。

### 原始任务
为下面的产品问题选择最优方案。

### 待处理内容
"""
{用户输入的产品问题}
"""

### 思维树配置
- Thought 粒度：一个可执行的产品策略或方案假设
- 搜索策略：beam
- 每轮候选数：3
- 最大迭代深度：3
- 每轮保留分支数：2
- 评价标准：用户价值、实现成本、风险、长期可扩展性
- 决策规则：选择综合评分最高的分支；如果两个分支互补，则合并成一个最终方案。

### 输出要求
- 使用 Markdown 表格展示思维树过程。
- 最后输出“最终方案”和“选择理由”。
- 回答不超过 800 字。

### 约束条件
- 不要提出明显超出资源约束的方案。
- 剪枝理由要简短明确。

### 执行方法
1. 初始化根节点：把原始任务作为根状态。
2. 第 1 到 3 轮：
   - 从每个保留状态生成最多 3 个候选 thought。
   - 用评价标准为每个候选打分或给出等级。
   - 剪枝明显违反约束、不可行、重复或低价值的候选。
   - 保留最多 2 个最有希望的状态进入下一轮。
   - 如果已经得到满足输出要求的高置信答案，可以提前停止。
3. 如果保留分支陷入死路，回溯到上一轮次优分支重新展开。
4. 最终根据决策规则选择或综合答案。
5. 输出控制：展示候选摘要、评分、剪枝原因和最终答案。
```

### 解释

- Thought 粒度明确为“产品策略”。
- 分支数、深度、保留数都受控。
- 有评分、剪枝和合并规则，是真正接近 ToT 的提示结构。

## 示例2：专家协作式 ToT

### 用户任务及输出格式

任务：回答一个复杂逻辑问题。

输出格式：Markdown 表格，最后输出结论。

### 生成的思维树 Prompt

```
你是一名主持多专家推理的逻辑问题求解助手。

请使用专家协作式 Tree of Thoughts 方法处理任务。你将模拟 3 位不同视角的专家，每位专家在每轮提出一个候选 thought；随后所有候选会被评价、剪枝和合并。专家只是产生多样化分支的方式，最终必须遵守统一的评价和决策规则。

### 原始任务
回答下面的复杂逻辑问题。

### 待处理内容
"""
{用户输入的问题}
"""

### 专家角色
- 专家 A：形式逻辑与约束检查
- 专家 B：反例搜索与风险识别
- 专家 C：综合归纳与最终表达

### 思维树配置
- Thought 粒度：一个可检验的推理步骤或候选解释
- 最大迭代深度：3
- 每轮保留分支数：2
- 评价标准：逻辑一致性、证据覆盖、是否满足题目约束、是否存在反例
- 决策规则：优先选择无反例且约束覆盖最完整的分支；若专家 C 综合多个分支，必须说明综合来源。

### 输出要求
使用 Markdown 表格展示过程，最后输出“最终答案”。

### 约束条件
- 每轮每位专家只提出一个候选。
- 明显错误的分支必须退出或被剪枝。
- 不要输出冗长隐藏思维链，只输出可公开的推理摘要。

### 执行方法
1. 每位专家在当前轮次提出 1 个候选 thought，必须考虑上一轮保留分支。
2. 专家可以指出自己或其他分支的错误；发现明显错误的分支应退出或被剪枝。
3. 对所有候选按评价标准打分，保留最多 2 个分支。
4. 重复最多 3 轮；若已有高置信结论，可提前停止。
5. 最终按决策规则选择或综合答案。
6. 输出控制：展示候选摘要、互相修正、评分和最终答案。
```

### 解释

- 这个版本吸收了用户给出的“三个专家”提示，但补上了 ToT 必需的搜索控制。
- 专家角色有分工，减少重复。
- 表格字段固定，便于解析和比较。

## 示例3：严格输出场景

### 用户任务及输出格式

任务：为一段代码选择最可能的 bug 原因和修复方案。

输出格式：只输出 JSON。

### 生成的思维树 Prompt

```
你是一名严谨的代码诊断助手。

请用紧凑版 Tree of Thoughts 处理任务：生成 3 个候选方案，按评价标准评分，保留最优 2 个并最多迭代 2 轮，最后按决策规则输出答案。不要展开冗长推理，只输出候选摘要、评分和最终答案。

### 任务
诊断下面代码的 bug，并给出修复方案。

### 待处理内容
"""
{用户输入的代码和报错}
"""

### 评价标准
可复现性、与报错匹配度、修复风险、改动范围

### 输出要求
只输出 JSON 对象：
{
  "likely_cause": "...",
  "fix": "...",
  "confidence": "...",
  "alternatives_considered": ["..."]
}

### 约束条件
- 不要输出 Markdown 代码块。
- 不要输出过程性解释。
- 如果证据不足，confidence 使用 "low"。

### 决策规则
选择与报错最匹配且修复风险最低的分支；把被剪枝但仍有参考价值的分支放入 alternatives_considered。
```

### 解释

- ToT 可以内部执行，最终仍满足严格 JSON。
- 分支探索用于提升诊断质量，但不污染用户要求的输出格式。

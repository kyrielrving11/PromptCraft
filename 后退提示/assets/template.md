# 后退提示模板

## 论文机制提炼

Step-Back Prompting 的关键流程：

1. 先从包含大量具体细节的原问题中“后退”一步。
2. 生成一个更高层、更通用、更容易回答的后退问题。
3. 回答后退问题，提取相关概念、原则、公式、背景事实或判断框架。
4. 以这些抽象内容为依据，回到原始问题的具体细节进行推理。
5. 最终答案必须直接回答原始问题，而不是只停留在抽象层。

它和问题拆解不同：问题拆解通常向下拆成多个低层子问题；后退提示向上抽象成一个高层问题或原则。

## 生成 Prompt 的原则

1. 在角色中强调“后退抽象”和“基于抽象回到原题推理”。
2. 支持零样本：没有案例时，也要明确告诉模型如何生成后退问题和抽象依据，并说明“未检测到用户案例，因此按零样本后退提示生成”。
3. 支持可选案例：有案例时，案例只用于展示抽象方式，不应覆盖用户当前任务；不要因缺少案例而追问。
4. 后退问题要精准：比原题更通用，但仍能提供解决原题所需的信息。
5. 抽象依据要可用：输出原则、定义、公式、背景事实、判断标准或检索查询方向。
6. 推理阶段要防止上下文丢失：最终答案必须逐项对齐原始问题、条件和输出格式。
7. 对严格格式输出，后退过程可以内部完成，最终只输出目标格式。

```markdown
#### 案例 1

"""

"""

"""
更高层、更通用的问题
"""

抽象依据：
"""
相关原则、概念、背景事实或通用框架
"""

最终答案：
"""
如何基于抽象回到原题得到答案
"""
```

## 逐步生成方法

1. 读取任务、待处理内容、输出格式、约束和可选案例。
2. 判断任务是否需要抽象：多细节、多跳、知识密集、专业原则密集的任务优先使用。
3. 选择单轮模板或两阶段模板。
4. 如果有案例，格式化案例；如果没有案例，写明零样本后退策略。
5. 写清后退问题的生成标准：更高层、更通用、覆盖原题。
6. 写清抽象依据的类型：原则、公式、背景事实、判断标准、检索方向。
7. 写清最终答案必须回到原题，并遵守输出格式。

## 常见 Gotchas

- 后退问题太宽泛：会导致泛泛而谈。应收紧到能覆盖原题的最小通用层。
- 后退问题太狭窄：只是复述原题。应继续上升到原则、历史、定义或通用框架。
- 抽象依据正确但忘记回到原题：必须添加“最终答案直接回答原始问题”的约束。
- 事实型任务缺少证据：可把后退问题作为检索查询方向，并在最终答案中标注证据不足。
- 严格格式任务：不要展示过程，让模型内部完成后退和推理后只输出目标格式。
